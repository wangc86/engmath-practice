# 一個新工作階段的第一個提示詞（樣板）

> **用途**：在一台新機器、或一個新的 AI 工作階段上接手這個專案時，
> 把下面「可以直接貼的提示詞」整段複製過去。
>
> ⚠️ **它刻意不是一個實作任務。** 第一個提示詞要做的是**交接驗收**：
> 證明新環境跑得起來、證明接手的人（或 AI）讀懂了規則，然後才動程式碼。
> 一上來就實作，等於在一個沒有驗證過的環境裡改一個有一千多項測試的專案
> ——而那些測試如果因為環境問題而紅，很容易被誤判成「我改壞了」。

---

## 事前：把資料夾接上

**同一台機器**：在 Cowork 裡選 `~/code/engmath-practice` 這個資料夾。

**另一台機器**（或雲端工作階段）：

```bash
git clone https://github.com/wangc86/engmath-practice.git
cd engmath-practice
```

然後在 Cowork 裡選那個資料夾。

> ⛔ **換機器不只是 clone。** 還要建 venv、裝 Node.js、產一把新的 SSH 金鑰、
> 在那台電腦上授權刪檔，而且第一次跑測試會是**全跑**（那是對的，理由見下）。
> **完整的清單與驗收在 [`../MOVING-MACHINES.md`](../MOVING-MACHINES.md)。**
> ⚠️ 其中最容易咬人的一項：**沒裝 Node.js 的話 406 項是被跳過而不是變紅**，
> 全套會印 `888 passed, 406 skipped` 而看起來很安全。

⚠️ **選的是 repo 的根目錄**（含 `CLAUDE.md`、`PLAN.md`、`app/` 的那一層），
不是它的上層。選錯的症狀是 AI 找不到 `CLAUDE.md`，於是它會**用一般的
方式開始寫程式**——而這個專案幾乎每一條慣例都與「一般的方式」不同。

## 可以直接貼的提示詞

> 這是一個已經進行了三十輪的專案，你是接手的第一個工作階段。
> **在動任何程式碼之前，先完成下面的交接驗收。**
>
> ## 一、開工的三件事（順序有意義）
>
> 1. 把這段提示詞原文存成 `dispatches/<今天日期>-handover.md`
>    （格式見 `dispatches/README.md`）。
> 2. `python scripts/turnaround.py start <任務編號> --estimate <人週>`。
> 3. 讀 `CLAUDE.md` **全文**，特別是九條硬規則裡的**第九條**
>    （回報必須是真的），以及那一長串「已經不存在了」的清單。
>    ⚠️ 那份清單防的是一件真的會發生的事：照著一個已經作廢的設計往下寫。
>
> ## 二、環境探測（這一步決定後面做什麼）
>
> `CLAUDE.md` 開頭寫著一條很重的環境限制：**先前的工作環境不允許刪檔
> （unlink）**，因此這個專案長出了三個慣例——`scripts/git-safe-commit.sh`、
> `.attic/`、以及「刪掉一個檔案」實際上只能做到「改名搬走」。
>
> **請先確認你現在這個環境有沒有同樣的限制**：
>
> ```bash
> cd <專案根目錄> && touch .probe && rm .probe && echo "可以刪檔" || echo "不能刪檔"
> ```
>
> 回報結果。**這個答案會改變下面第四節該做什麼**，所以不要跳過。
>
> ## 三、交接驗收（證明環境是好的）
>
> 1. 建 venv、裝相依、跑**全部測試**（⚠️ 現行項數以 `PLAN.md` §1.7 為準——
>    寫死在這裡的數字上一次就過期了，所以現在不寫死）。
>    ⚠️ 若單次指令有時間上限，`tests/test_generators.py` 要分批跑，
>    切法寫在 `CLAUDE.md`。
> 2. 起 `uvicorn app.main:app`，確認 `/healthz` 回 `{"status":"ok"}`、
>    出題頁的下拉選單依**課程週次**分組、隨便出一題確認答案是收合的。
> 3. `git status` 必須是乾淨的，`git tag -l` 必須看得到 `grading-v1`
>    與 `hosted-v1` 兩個。⚠️ **看不到 tag 就先停下來回報**——那兩個 tag
>    是被拆掉的功能唯一的取回途徑，而 `PLAN.md` 裡有十幾處引用它們。
>
> **三項有任何一項不過，先回報再說，不要自己修。**
>
> ## 四、第一件工作
>
> 依第二節的結果二選一：
>
> **（a）如果這個環境可以刪檔** → 做 PLAN §6 階段 2A 的工作項 **2a0**
> （`app/generator/` 切子目錄，D16，估 0.1 PW）。
> 它被「不能刪檔」擋了十幾輪，是這個專案裡唯一一項**純粹被環境擋住**
> 的工作。⛔ **驗收標準只有一條，但它是硬的：`REGISTRY` 的鍵在遷移前後
> 逐字相同**——`template_id` 與檔案路徑從來沒有耦合過（D16 寫得很清楚），
> 所以搬檔案**不得順手改任何 `template_id`**。搬完把 `README.md` 的
> 「專案結構」與那幾處「⚠️ 過渡狀態」的註記一起更新。
>
> **（b）如果這個環境仍然不能刪檔** → 據實回報，然後改做
> `VERIFY-CHECKLIST.md` §A6（工作項 **2c**：逐步解答的整體人工審查）的
> **準備工作**：用 `scripts/preview.py` 產出全部 16 個題型 × 3 個難度的
> 樣本，並依 §A6 的判準先做一輪機器讀得出來的初篩（步驟顆粒度是否一致、
> `note` 是不是在回答「為什麼」而不是重述「做了什麼」），把可疑的列成
> 一份清單給老師逐題看。⚠️ **不要自己改敘述**——2c 的判斷是老師的。
>
> ## 五、收尾（每一輪都一樣）
>
> - 全部測試綠燈、`scripts/git-safe-commit.sh` 分 commit 提交
>   （⚠️ **路徑參數要放在 `--` 後面**，否則它會 `git add -A` 把整輪塞進
>   一個 commit）。
> - 更新 `PLAN.md`（新的 D 決定、§1.7 的測試項數）、`README.md`、
>   `CLAUDE.md`、`TURNAROUND.csv`。
> - ⚠️ **不要把 git 的輸出接到 `head`**——SIGPIPE 會讓腳本在產生 commit
>   之前就死掉，而它看起來像成功了。
>
> ## 六、回報
>
> 依第九條硬規則：決定與理由、測試數字、turnaround、**踩到的坑**
> （沒踩到就據實說沒有）、**還不夠穩的地方**。
> **不要為了讓回報好看而製造或誇大任何東西。**

## 之後每一輪

不需要再走交接驗收，回到 `dispatches/README.md` 的一般流程即可：
**存提示詞 → `turnaround.py start` → 讀 `CLAUDE.md` 與 `PLAN.md` 相關章節 →
動手 → 測試 → 提交 → 回報。**
